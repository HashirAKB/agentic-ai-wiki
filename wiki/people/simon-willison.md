## Agentic Engineering Patterns (guide, started Feb 2026)
A book-shaped, growing guide on getting good results from coding agents like Claude Code and Codex.

- **Agentic engineering vs vibe coding:** experienced engineers using agents to amplify their expertise, as opposed to not caring about the code.
- **Writing code is cheap now:** producing new code is nearly free, but good code still costs real effort; build new habits around that.
- **Hoard things you know how to do:** keep a collection of working examples and techniques so agents can recombine them.
- **AI should help us produce better code:** use agents to pay down tech debt, consider more options, and run a compound engineering loop.
- **Anti-pattern:** don't push unreviewed agent code onto collaborators.
- **Working with agents:** understand how agents work (LLM + system prompt + tools in a loop, token caching), use Git deliberately with agents, use subagents (explore, parallel, specialist).
- **Testing and QA:** red/green TDD (test first so agents write tighter, more reliable code), first run the existing tests, agentic manual testing (browser automation, have agents take notes).
- **Understanding code:** linear walkthroughs of a codebase and interactive explanations generated by the agent.
- **Annotated prompts and his prompt library** (proofreader, alt text, artifacts).

## Chapter notes (primary pages)
- **Red/green TDD:** write tests first, run them and confirm they fail, then implement until green. Skipping the red step risks a test that already passes and proves nothing. The prompt suffix "Use red/green TDD" is enough, because current models treat it as shorthand for the whole workflow. It guards against agent code that is broken or never used.
- **First run the tests:** open a session on an existing project with "First run the tests" (or the exact test command). Three effects: the agent discovers and keeps rerunning the suite; the test count hints at project size; and it sets a testing mindset so the agent adds tests for its own changes. Tests used to be costly to write and maintain; agents make that cost small, so the old excuses are gone.

- **Agentic manual testing:** passing automated tests does not prove the software works; have the agent actually run it (`python -c` snippets, scratch programs in `/tmp`, curl against a dev server, asking it to explore rather than verify one thing). Turn every bug found into a permanent test via red/green TDD. For web UIs use real browser automation (Playwright, agent-browser, his Rodney) and have the agent review screenshots; agents can also maintain brittle browser tests. His Showboat tool records commands with real output so the agent reports what happened, not what it expected.

- **Subagents:** a subagent is a fresh copy of the agent with its own context window and a focused prompt; the parent waits like on any tool call. Its main value is protecting the parent's context (quality tends to be better well under the maximum window). Three patterns: *explore* (map the repo and return file locations and line numbers before editing), *parallel* (independent edits across many files, possibly with a cheaper fast model), *specialist* (code reviewer, test runner that reports only failures, debugger). Caveats: do not create dozens of specialists; the root agent can often review or debug its own work if it has context left; parallelism only helps for genuinely independent tasks.

- **Anti-pattern: inflicting unreviewed code on collaborators.** Opening a PR of agent-generated code you have not reviewed or tested makes reviewers the first line of quality control, and they could have prompted an agent themselves. Before asking for review: it works and you are confident of that; it is small (agents can split work into separate commits); it explains the goal and links issues; you have read any agent-written description. Include evidence of your own review such as manual-testing notes, comments on key choices, or screenshots/video.

- **Linear walkthroughs:** to understand unfamiliar or vibe-coded code, have the agent read the repo and write a structured Markdown walkthrough. It should pull code with shell commands (via his Showboat `exec`/`note` tools) rather than retyping snippets, so nothing is hallucinated. His example: a SwiftUI app he never read became a walkthrough that taught him the ecosystem. He argues this offsets the worry that LLMs slow skill-building.

## Security: the lethal trifecta (primary post, Jun 2025)
- Three capabilities that are dangerous together: access to private data, exposure to untrusted content, and a way to send data out. With all three, an attacker can instruct the agent to leak the data.
- Root cause: LLMs cannot reliably separate operator instructions from instructions embedded in content they read.
- Mitigations: avoid combining the three (the only dependable protection for users); after an agent ingests untrusted input, constrain it so that input cannot trigger consequential actions; architectural approaches such as Google DeepMind's CaMeL. He argues that guardrail products with a "95%" catch rate are not good enough, and that mixing MCP tools makes accidental trifectas easy.

## Security follow-up: Rule of Two and adaptive attacks (primary post, 2025-11-02)
Source: https://simonwillison.net/2025/Nov/2/new-prompt-injection-papers/
- Meta's "Agents Rule of Two": in one session an agent should have at most two of (A) untrusted inputs, (B) access to sensitive systems or private data, (C) ability to change state or communicate externally. If a task needs all three, no autonomous run: use a fresh context or supervision such as human approval.
- Willison's take: a clearer way to explain the risk than his trifecta, and wider in scope. The trifecta covers only data exfiltration; state changes triggered by untrusted input are a separate harm.
- He objected to Meta's first diagram calling untrusted input plus state change "safe", since harm needs no private data. Meta replied that B means any sensitive system, so a sandboxed agent isolated from anything that matters can legitimately drop B.
- Paper "The Attacker Moves Second" (Oct 2025, authors from OpenAI, Anthropic and Google DeepMind): adaptive attacks (gradient, RL, search, human red-teaming) beat all 12 published defenses, most above 90% success, where the defenses had reported near zero on static attacks. His conclusion: system design, not filters, is the answer for now.
